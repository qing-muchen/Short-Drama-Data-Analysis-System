# Phase 5 新模块设计提案

## 1. 当前系统能力与缺口

当前系统已经形成一条较完整的数据分析链路：

```text
运营数据采集
  ↓
数据质量治理
  ↓
综合评价 / 趋势预测 / 异常发现
  ↓
分析展示
```

现有能力边界如下：

| 模块 | 主要回答的问题 | 当前能力 |
| --- | --- | --- |
| Score | 当前短剧综合表现如何 | Heat、Growth、Engagement、Lifecycle 和综合等级 |
| Data Quality | 数据是否可信 | 规则结果、四维质量分和质量等级 |
| Prediction | 下一步可能怎样变化 | Moving Average V1.0 下一日累计播放量预测，并支持历史 revision 追溯 |
| Anomaly | 当前行为是否偏离正常范围 | Rule-based Detection、异常证据和状态管理 |

因此系统仍缺少“如何采取运营行动”和“如何管理运营资源”的能力。尤其是：

- 分析结果尚未形成可跟踪的运营任务闭环。
- 平台、标签、短剧之间缺少面向运营的配置和效果归因视图。
- 预测和异常结果可以被查看，但缺少统一的行动优先级与处理时限。
- 尚未形成面向决策的方案、目标和实际结果对比。

Phase 5 应补齐决策支持和闭环管理，不能再次实现评分、质量评分、播放量预测或异常检测。

## 2. 候选模块总览

本轮调研提出四个候选方向：

1. 运营行动与告警处置中心
2. 短剧运营目标与效果复盘
3. 平台/标签运营策略分析
4. 数据血缘与分析解释中心

## 3. 候选一：运营行动与告警处置中心

### 3.1 解决的问题

Score、Data Quality 和 Anomaly 已能产生结果，但结果主要停留在展示层。运营人员仍需手工记录“谁处理、何时处理、采取了什么措施、是否完成”。本模块将异常和质量问题转化为可分派、可跟踪、可关闭的运营行动。

### 3.2 用户价值

- 统一管理异常、质量问题和评分低于阈值的待办事项。
- 支持负责人、优先级、截止时间、状态和处理说明。
- 形成从发现到处置的审计链，提升软件著作权项目的业务闭环完整性。
- 可按逾期、严重等级和负责人生成运营工作量视图。

### 3.3 数据库影响

建议新增三类实体：

- `operation_tasks`：任务主体、来源类型、来源记录、负责人、优先级、状态和时间字段。
- `operation_task_comments`：处理过程和人工说明。
- `operation_task_events`：状态、负责人和优先级变化历史。

任务表不复制短剧名称、异常证据或质量评分；通过来源类型和来源 ID 引用已有结果，并保存创建时的必要摘要以避免历史解释丢失。需要新的 Migration、ORM、Repository、Service、API 和 Dashboard。

### 3.4 依赖与复杂度

依赖 Phase 2 的质量问题、Phase 4 的异常记录和现有 `operation_logs`，可选读取 Phase 1/3 的结果作为任务来源。架构保持：

```text
Router → OperationTaskService → OperationTaskRepository → ORM/Database
```

复杂度：中等。主要风险是跨模块来源引用、状态机和权限设计；不能让任务模块重新判断异常或质量等级。

## 4. 候选二：短剧运营目标与效果复盘

### 4.1 解决的问题

现有模块描述“当前状态”和“可能趋势”，但缺少运营目标管理。例如某平台希望在指定周期达到播放量、互动率或质量目标，系统需要比较目标、实际结果和偏差。

### 4.2 用户价值

- 支持按短剧、平台或标签制定周期目标。
- 展示目标完成率、实际偏差和阶段复盘结果。
- 将 Score、Prediction 和 Anomaly 作为复盘证据，而不是重新计算这些指标。

### 4.3 数据库影响

建议新增：

- `operation_goals`：目标主体、指标、目标值、周期和作用域。
- `operation_goal_snapshots`：按分析日期保存目标实际值和完成状态。

如果目标支持平台或标签作用域，需要复用现有实体外键并明确互斥约束。需要 Migration、ORM、Calculator（只做完成率和偏差计算）、Repository、Service、API 和 Dashboard。

### 4.4 依赖与复杂度

依赖 AnalyticsService 提供实际指标，读取 Score/Prediction/Anomaly 作为复盘上下文。复杂度：中高。主要风险是目标口径、周期边界、作用域模型和实际值的历史追溯；不能把目标完成率伪装成综合评分。

## 5. 候选三：平台/标签运营策略分析

### 5.1 解决的问题

系统已经保存平台、标签和多对多关系，但现有分析重点仍偏向单剧。运营人员缺少“哪些平台或内容标签更适合某类短剧”的结构化比较。

### 5.2 用户价值

- 比较平台和标签下的作品数量、质量、评分、增长和异常概况。
- 为排播、内容组合和平台运营提供证据。
- 复用已有事实和分析结果，减少重复数据表。

### 5.3 数据库影响

V1 原则上不新增运营事实表。可通过 AnalyticsService 的聚合查询完成；若需要保存周期性聚合快照，可新增 `strategy_analysis_snapshots`，但应在确认查询性能问题后再引入。通常需要新 Calculator（聚合指标）、Service、API 和 Dashboard，Migration/ORM 可选。

### 5.4 依赖与复杂度

依赖 `drama_platforms`、`drama_tags`、Score、Quality、Prediction 和 Anomaly。复杂度：中等。主要风险是样本量不足导致误读、平台重复归属和标签交叉聚合；该模块不能重新定义 Heat 或综合评分公式。

## 6. 候选四：数据血缘与分析解释中心

### 6.1 解决的问题

当前质量、评分、预测和异常结果虽然保留了算法版本和分析时间，但普通用户难以回答“这个数字来自哪些 snapshot、使用了哪个规则版本、为什么得到这个结果”。本模块提供面向审计和教学的软件解释链。

### 6.2 用户价值

- 查看结果到输入数据、revision、规则和算法版本的追溯路径。
- 对单个评分、预测或异常提供可读的计算证据和版本信息。
- 提升软件著作权材料中的数据治理、可解释性和可审计性。

### 6.3 数据库影响

V1 优先利用已有 `analysis_as_of`、`algorithm_version`、规则结果和 `operation_logs`，不新增表。若现有字段不足，再考虑通用 `analysis_evidence_links`，其中保存结果类型、结果 ID、来源实体类型、来源 ID 和证据摘要；禁止复制原始运营事实。需要新 Service、API 和解释页面，Migration/ORM 视证据缺口决定。

### 6.4 依赖与复杂度

依赖四个既有模块的结果和版本元数据。复杂度：中等。主要风险是跨模块统一标识、敏感信息暴露和证据快照体积；解释中心不能改变任何已有计算结果。

## 7. 架构影响比较

| 候选 | 新表 | 新 ORM | 新 Calculator | 新 API | 新 Dashboard | 复杂度 | 主要风险 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 运营行动与告警处置 | 是 | 是 | 否或仅状态机 | 是 | 是 | 中 | 跨模块来源、权限和状态流转 |
| 目标与效果复盘 | 是 | 是 | 是（偏差/完成率） | 是 | 是 | 中高 | 目标口径、周期和作用域 |
| 平台/标签策略分析 | V1 可否 | 可选 | 是（聚合） | 是 | 是 | 中 | 样本偏差、交叉归属 |
| 数据血缘与解释中心 | V1 否 | V1 否 | 否 | 是 | 是 | 中 | 统一证据标识、信息暴露 |

四个候选都可保持 `Router → Service → Repository → Database`。其中策略分析和解释中心应优先复用已有数据，避免为展示目的重复建设事实表。

## 8. 推荐方向：运营行动与告警处置中心

推荐 Phase 5 首先实现“运营行动与告警处置中心”。理由如下：

1. **互补性最强**：它不重复 Score、Data Quality、Prediction 或 Anomaly，而是消费这些模块的输出，补上“分析结果到运营行动”的缺口。
2. **系统闭环最清晰**：现有链路是采集、治理、分析和发现；任务中心增加分派、处理、复核和审计，形成可展示的决策支持闭环。
3. **实现边界明确**：任务模块不计算评分、不判断异常、不修改质量规则，只管理来源、状态、责任人和处理证据。
4. **扩展空间充分**：后续可加入 SLA、通知、批量分派、目标复盘和策略推荐，但不会阻塞当前模块。
5. **软件著作权价值高**：可体现系统从数据处理和分析向运营协同、过程管理和决策支持延伸。

推荐的 V1 来源范围为 Phase 2 的 ERROR 质量问题和 Phase 4 的 A/B 级异常；Score/Prediction 仅作为详情上下文，不自动创建任务。这样可以控制初期范围，避免把所有分析结果都转化为噪声任务。

## 9. 推荐方向的后续设计边界

后续进入正式设计时应先冻结：

- `source_type` 枚举及来源记录唯一性。
- 任务状态机和允许的状态转移。
- 负责人权限与管理员权限。
- SLA 截止时间及逾期规则。
- 任务与 `operation_logs` 的事务边界。
- 是否保存来源证据快照，以及快照与原记录的关系。

建议实现顺序为：设计评审 → V012 Migration/ORM → Task Repository → Task Service → API → Dashboard → 集成测试。当前阶段不创建表、不修改 ORM，也不进入实现。

## 10. 结论

Phase 5 推荐方向为运营行动与告警处置中心。该方向建立在四个已完成模块之上，解决现有系统“发现问题但缺少跟踪处置”的业务缺口，同时保持现有分层架构和历史结果不可变原则。本文仅为需求分析和设计规划，不代表已批准进入编码阶段。
