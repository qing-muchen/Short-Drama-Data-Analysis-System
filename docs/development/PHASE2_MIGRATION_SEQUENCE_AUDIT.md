## 2. 每个迁移职责

### 2.1 V001：核心与主数据

新增表：

- `users`
- `dramas`
- `actors`
- `directors`
- `companies`
- `platforms`
- `tags`

主要约束：

- 各表自增主键。
- 用户名、短剧编码、平台名称、标签名称唯一。
- 名称和编码非空白。
- 用户角色、实体状态、短剧状态为限定枚举。
- 集数和单集时长必须为正数或NULL。

业务目的：建立用户、短剧及演员、导演、公司、平台、标签等主数据基线，为后续关系、快照和评分提供被引用实体。

### 2.2 V002：业务关系与平台发布

新增表：

- `drama_actors`
- `drama_directors`
- `drama_companies`
- `drama_tags`
- `drama_platforms`

主要约束与关系：

- 建立短剧与演员、导演、公司、标签、平台的外键关系。
- 使用业务唯一约束防止同一关系重复。
- 演员番位、公司参与类型、关系状态和发布状态受到CHECK约束。
- 非PLANNED发布关系必须具有`online_at`。

业务目的：以关联表表达多对多关系，并建立短剧在各平台的发布实体，避免主数据表出现反范式字段。

### 2.3 V003：运营快照与不可变revision

新增表：

- `drama_metric_snapshots`
- `drama_metric_snapshot_revisions`

修改约束：

- 创建revision表后，通过`ALTER TABLE drama_metric_snapshots`补充“当前revision必须属于同一snapshot”的复合外键。
- 创建禁止更新、禁止删除revision的两个触发器。

主要约束与关系：

- 同一短剧平台和快照时间只能有一个观察槽位。
- revision版本号在同一snapshot内唯一。
- previous revision必须属于同一snapshot。
- INITIAL/CORRECTION/VOID链路、变更原因、播放量和排名均有约束。

业务目的：将稳定观察槽位与不可变指标revision分离，保存运营指标历史和修订链。

### 2.4 V004：导入与质量问题治理

新增表：

- `import_jobs`
- `import_errors`
- `data_quality_issues`

修改约束：

- 通过`ALTER TABLE drama_metric_snapshots`增加`source_import_job_id`到`import_jobs`的外键。
- V004曾在提交`1bb6e02`中修订，以处理MySQL保留关键字冲突；当前文件是修订后的正式版本。

主要约束与关系：

- Import任务类型、状态、格式、行数关系和起止时间受到约束。
- Import Error必须属于一个Import Job，并支持行号、错误编码和原始值定位。
- Data Quality Issue必须且只能关联snapshot revision、drama platform、drama三类目标中的一个。
- 质量问题类型、严重度、状态、来源、检测时间和处理元组受到约束。

业务目的：形成导入任务、错误定位和持续性质量问题的治理基础，并建立运营快照的数据来源追踪。

### 2.5 V005：不可变操作日志

新增表：

- `operation_logs`

主要约束与关系：

- 日志必须具有操作用户。
- 日志必须且只能关联一个支持的业务目标。
- 操作结果限定为SUCCESS或FAILURE。
- 操作类型和摘要不能为空白。
- 两个触发器禁止更新和删除日志。

业务目的：为用户、主数据、关系、快照、Import和质量问题操作提供统一、追加式审计记录。

### 2.6 V006：查询索引

新增表：无。

修改约束：无业务CHECK或外键变更。

新增内容：当前文件包含46条独立`CREATE INDEX`语句，覆盖：

- 用户与主数据状态/名称查询。
- 短剧关联与平台发布查询。
- 快照来源和revision时间查询。
- Import Job与Import Error查询。
- Data Quality Issue状态、目标和处理查询。
- Operation Log操作人、类型、request及目标查询。

V006曾与V004一起在`1bb6e02`中修订，以适配修订后的物理字段命名。

业务目的：为当前CRUD、导入、质量问题、快照和审计查询提供数据库索引，不引入新业务实体。

### 2.7 V007：批量导入编排候选迁移

当前文件状态：工作区存在，但未被Git跟踪，不能视为正式迁移。

候选SQL内容：

- 新增`import_batches`表。
- 保存批次编码、状态、创建人、文件数、行数统计和各阶段时间。
- 为批次编码、状态、行数关系和时间关系增加约束。
- 通过`ALTER TABLE import_jobs`增加：
  - `import_batch_id`
  - `batch_sequence`
  - `batch_file_type`
- 增加批次外键、批次内顺序唯一、批次内文件类型唯一、批次字段完整性CHECK和批次状态索引。

业务目的：从单文件Import Job之上增加多文件Import Batch编排元数据。

审查边界：以上只是对现有未跟踪SQL内容的客观描述；该文件是否已完成业务验收、数据库验证或计划正式发布，**待确认**。

### 2.8 V008：短剧综合评分

新增表：

- `drama_scores`

主要约束与关系：

- 外键`drama_id`引用V001创建的`dramas`。
- 业务唯一键覆盖短剧、评分日期、算法版本和作用域。
- Phase 1作用域固定为`ALL / 0`。
- Heat、Growth、Engagement、Lifecycle和Total均限制为0—100。
- 等级限制为S/A/B/C，算法版本不能为空白。
- 建立排行和等级分布索引。

业务目的：持久化Composite Score V1.0结果，为Score API和Score Dashboard提供历史评分、排行与详情数据。

## 3. V007问题分析

### 3.1 文件是否缺失

结论分两个层面：

- 文件系统层面：**不缺失**。当前工作区存在`V007__create_import_batches.sql`。
- 正式Git版本层面：**缺失**。该文件未被跟踪，HEAD和所有可见Git历史中都不存在V007迁移。

因此，其他开发者、CI或部署环境从当前Git版本检出代码时，只会得到V001—V006和V008，不会得到当前工作区的V007。

### 3.2 是否被其他迁移替代

在已检查的V001—V006、V008和DDL基线中：

- 没有其他SQL创建`import_batches`。
- 没有其他SQL向`import_jobs`增加候选V007中的三个批次字段。
- `git log --all`没有发现包含`CREATE TABLE import_batches`或`import_batch_id`的数据库提交。

仓库证据表明V007**未被其他正式迁移替代**。

是否存在仓库之外的手工SQL或数据库变更：**待确认**。

### 3.3 是否存在编号错误

- V008文件名为`V008__create_drama_scores.sql`。
- 文件内部注释明确写为“Migration V008”。
- Git提交`80b389b`以V008名称正式归档。
- V008内容属于Phase 1综合评分，与候选V007的批量导入职责不同。

没有证据表明V008只是误写成V008、实际应为V007。V008编号是有意选择还是当时预留了V007：**待确认**。

### 3.4 是否影响V008

直接SQL依赖：**不影响**。

- V008只创建`drama_scores`。
- V008唯一外键引用V001已经创建的`dramas`。
- V008不引用`import_batches`，也不引用候选V007向`import_jobs`增加的字段。
- 候选V007同样不引用`drama_scores`。

因此，在空数据库已经执行V001—V006的前提下，从SQL依赖关系看可以直接执行V008。

迁移治理与部署一致性：**存在影响**。

- 按文件名执行的不同环境可能得到“含V007”和“不含V007”两种schema。
- 仓库没有schema history机制，无法自动识别某个环境是否手工执行过候选V007。
- 后续V009若默认V001—V008全部正式存在，会掩盖V007的真实状态。
- 将来恢复V007时，已存在`import_batches`或已新增列的环境可能重复执行失败。

结论：V007缺口不会使V008的建表SQL失效，但会使V009之前的正式迁移基线不确定。

## 4. V009接入建议

### 4.1 方案A：恢复V007

做法：将当前候选V007作为独立任务进行业务、SQL、ORM和MySQL约束验证；确认内容正确后，以独立Git提交纳入正式序列，再创建V009。

优点：

- 恢复V001—V009连续序列。
- 保留批量导入迁移原本占用的版本号。
- 与当前工作区的批量导入相关文件方向一致。
- 不需要修改已经归档的V008。

风险与前置条件：

- 当前V007没有Git历史，不能直接认定为已审核版本。
- 必须确认V007与Import ORM、Service、测试及目标MySQL结构一致。
- 必须查询各实际环境是否已经手工执行过相同或不同内容的V007。
- 必须独立提交，不能与Phase 2 V009混合。
- 如果某环境已经存在相关表或列，需要制定基线确认或一次性修复步骤，不能盲目重复执行。

适用条件：批量导入功能确认需要保留，且当前候选SQL经独立审查和数据库验证后成为权威V007。

### 4.2 方案B：补充空迁移

做法：在确认V007业务已放弃且任何环境从未执行候选V007后，用只包含说明、不改变schema的V007占位迁移补齐序号。

优点：

- 以最小数据库变更补齐版本编号。
- 不影响V008现有表结构。
- 明确记录V007被保留或废弃，而不是让编号永久含糊。

风险与前置条件：

- 会放弃当前候选V007中的`import_batches`能力。
- 若有环境已经执行过实体V007，同一版本号对应两种内容，风险严重。
- 若当前批量导入代码依赖V007字段，空迁移无法满足代码运行要求。
- 必须先处置现有同名未跟踪文件，不能让实体V007与空V007并存。

适用条件：产品明确放弃该批量导入schema，且通过环境核查确认没有数据库执行过候选V007。

### 4.3 方案C：调整迁移序列

可能做法：将已经发布的V008重编号为V007，并把后续Data Quality迁移顺延或重编号。

优点：

- 在一个全新且从未部署的仓库中可以形成表面连续的文件编号。

风险：

- V008已经由Phase 1提交`80b389b`正式归档，并被后续文档和版本记录引用。
- 重命名已发布迁移会导致Git历史、文档、人工执行记录和潜在数据库记录不一致。
- 无法解决候选批量导入V007究竟保留还是废弃的问题。
- 如果任何环境已经按V008名称执行，重编号会制造新的版本歧义。

适用条件：只有在确认所有数据库均可销毁重建、V008从未被任何共享环境执行、且允许重写Phase 1发布历史时才可能考虑。当前仓库证据不足以满足这些条件。

审查意见：**不推荐方案C**。

### 4.4 方案比较

| 方案 | 连续性 | 保留批量导入 | 改动已发布V008 | 环境核查要求 | 推荐度 |
|---|---|---:|---:|---:|---|
| A. 恢复V007 | 是 | 是 | 否 | 高 | 首选，需先验证 |
| B. 空迁移 | 是 | 否 | 否 | 很高 | 条件性备选 |
| C. 调整序列 | 表面连续 | 待定 | 是 | 很高 | 不推荐 |

## 5. 最终建议

### 5.1 是否可以安全创建V009

当前结论：**暂时不可以安全创建V009**。

原因不是V008对V007存在直接SQL依赖，而是正式迁移基线尚未确定：

1. Git正式版本缺少V007。
2. 工作区存在一个未跟踪且未经本次任务验证的实体V007。
3. Git历史中没有V007提交，无法确认其来源和审批状态。
4. 仓库没有自动Migration history机制。
5. 实际数据库是否执行过候选V007无法从仓库确认。

### 5.2 推荐方案

优先选择方案A，但必须先建立证据：

1. 由批量导入模块负责人确认`V007__create_import_batches.sql`是否为预期最终结构。
2. 将候选V007与对应ORM、Service和测试逐项核对。
3. 在隔离MySQL 8.x中执行V001—V008全序列和约束测试。
4. 核查所有需要保留的数据库是否已经存在`import_batches`及三个Import Job批次字段。
5. 以独立提交恢复V007，不与V009或Phase 2代码混合。
6. 确认Git序列和目标数据库基线一致后，再创建V009。

如果产品明确确认批量导入迁移已经废弃，并且所有环境确认从未执行当前候选V007，才采用方案B。

不要采用方案C重编号已经归档的V008。

### 5.3 待确认事项

| 事项 | 当前状态 |
|---|---|
| 候选V007是否为批量导入最终SQL | 待确认 |
| 候选V007是否经过MySQL完整验证 | 待确认 |
| 开发数据库是否执行过候选V007 | 待确认 |
| 测试/演示数据库是否执行过候选V007 | 待确认 |
| 是否存在仓库外的V007版本 | 待确认 |
| 批量导入功能是否必须进入正式基线 | 待确认 |

以上事项明确前，Phase 2应停留在设计阶段，不创建或执行V009。
